# Changelog

## Unreleased

- Exact pins now drop files whose `Requires-Python` excludes the target Python, resolving per Python when several are checked and reporting `missing` with an `--explain` reason. (#291, thanks [@khizer-flow](https://github.com/khizer-flow))
- An empty Python version specification, such as `-p ""` or `-p ,` (or `python = [""]` in `[tool.wheelgap]`), is now an input error (exit 2) instead of checking zero targets and passing. (#289, thanks [@khizer-flow](https://github.com/khizer-flow))
- `--explain --notes` now reads the coverage tracker's per-Python notes: a note with a `python` list (such as `["3.13"]` or `["3.14t"]`) is shown only for gaps on those Pythons, and `--json` includes its `python`. Notes without one still apply to every Python, and a note with an invalid `python` is dropped. (#288, thanks [@khizer-flow](https://github.com/khizer-flow))
- `python -m wheelgap.scan` now adds, for packages Pyodide ships, `bundled_versions` (the version each lock ships, by Python), `bundled_version` (that version when every lock agrees, otherwise `null`) and `bundled_version_differs` (whether any differs from the release the scan checked) to each package entry. When a lock has no `info.version`, its Pyodide release is read from Pyodide's own release URL (`cdn.jsdelivr.net/pyodide/v0.29.5/…`, `github.com/pyodide/pyodide/releases/download/0.29.5/…`) or the file name (`pyodide-lock-0.29.5.json`), so `pyodide_version` and the CLI's "Pyodide …'s own builds" line name it instead of `?`. (#276, thanks [@chirag-gupta7](https://github.com/chirag-gupta7))
- Version ranges checked against several Python versions now select the newest matching release whose `Requires-Python` permits each Python major/minor. Reports show separate rows for distinct resolutions, keeping each one's eligible files and lookup errors separate, with `n/a` for targets using another resolution. This works with the PyPI JSON API, simple indexes, and the `check_lockfile()` API. (#275, thanks [@Swarneil1905](https://github.com/Swarneil1905))
- A `uv.lock` dependency edge with a field of the wrong type, such as `marker = 5`, is now an input error (exit 2) naming the file and the package, instead of a `TypeError` traceback from `packaging`. (#274, thanks [@Franky100-pig](https://github.com/Franky100-pig))
- Invalid package `markers` in `poetry.lock` now report an error naming the file and package instead of treating them as unconditional dependencies. (#272, thanks [@enidchen0125](https://github.com/enidchen0125))
- `wheelgap --suggest-targets [DIR]` suggests targets and Pythons from what the project already names. It reads `runs-on` in its GitHub Actions workflows (single labels and literal matrices, with `include` and `exclude`), the `python-version`, `freethreaded` and `architecture` given to `actions/setup-python` (or the `python-version` given to `astral-sh/setup-uv`), and the final stage of every Dockerfile and Containerfile, read as `--dockerfile` reads it. It prints each suggestion with the file and line it came from, then a `[tool.wheelgap]` snippet to paste into `pyproject.toml`, with `glibc` or `macos` when a pinned runner or image names it, and exits 0 without changing or checking anything. The snippet combines every job, so check it before pasting. A workflow is read only when every line is in a small subset of YAML whose meaning is certain; otherwise the file is listed as unread, with the first line that isn't. Whatever it can't read for sure (an expression, a computed matrix, a self-hosted runner, a job in a `container:`) is listed with its file and line instead of guessed. `--json` prints the same as an object. (#250)
- `--explain --build-info` (or `build-info = true`) says what each `source` build needs, from the `[build-system]` table in the sdist's `pyproject.toml`: `build needs: at least a Rust toolchain (maturin<2,>=1)`, `CMake and a C/C++ compiler (scikit-build-core)` or `a C/C++ compiler (cython)`, with every other requirement listed by name, and `no compiler` only for flit and poetry-core backends. `--json` adds `build_requires` to each package. It's off by default, since it downloads sdists, and only reads those known to come from PyPI, by the rule `--conda-forge` follows (a package whose lock records PyPI's index: from `uv.lock` or `pylock.toml`, fetched from the lock's `files.pythonhosted.org` URL and checked against its sha256, and from a `poetry.lock` legacy source or `pixi.lock` index of `https://pypi.org/simple`, through PyPI's JSON API; or a package wheelgap found on pypi.org itself from an input that names no other index; nothing in a run with `--index-url`, `WHEELGAP_INDEX_URL` or a pip or uv index setting, which a note says), as pip would unpack them, giving no answer where pip could read another file. It takes at most 30 seconds, never changes the exit code, and caches verified answers for 24 hours. (#249)
- `poetry.lock` (Poetry 2.x) inputs now accept `--extra NAME` and `--all-extras`, and the configured `extras`, with the meanings of `poetry install --extras NAME` and `--all-extras`: a package whose lock markers are only extra comparisons (`extra == "s3"`) counts only if one of those extras is selected, with extra names normalized as Poetry does (`Fancy_Name` is `fancy-name`). `--only-group main --extra api` works too, like `poetry install --only main --extras api`. An extra that isn't in the lock's `[extras]` table is an error, and so is `--extra` on a Poetry 1.x lock. Group selections now follow Poetry here as well, so `--no-dev` (or configured `groups`) on a `poetry.lock` no longer checks packages that only an extra installs. This matches what Poetry 2.3 and later install with default settings. Poetry 2.0-2.2 can install more than the lock's markers say, so where the lock alone can't tell, wheelgap checks a superset of what any Poetry 2.x installs, and a note on stderr says so: a package whose markers combine an extra with other conditions is checked as if any extra might be selected, and extras leave nothing out of a lock with no `pyproject.toml` beside it, or whose `pyproject.toml` also declares a name from an extra elsewhere (in the dependencies, a group, or another extra with a marker) or has a requirement wheelgap can't read. (#246)
- `--explain --notes` (or `notes = true` in `[tool.wheelgap]`) shows the [coverage tracker](https://wheelgap.github.io/tracker/)'s notes for a package with a gap, such as "use `psycopg2-binary`" or the system libraries to install first, under the explanation with their links and the date each was last checked. A note is shown only for the gap platforms it covers (`all` means the nine platforms the tracker scans), and a note limited to some releases only when your version matches. `--json --explain` adds a `notes` list to each package, and `--markdown` shows them as plain text in the collapsed section. It's opt-in because it sends the names of packages with gaps to wheelgap.github.io, so `--explain` on a lockfile still makes no requests; it then suggests `--notes` in one dim stderr line (not with `-q`) when there's a package it could look up. Only names that are positively PyPI packages are sent: a `uv.lock` or `pylock.toml` entry from pypi.org, or a name found on pypi.org whose input (and environment) names no other index; never `pdm.lock` or `poetry.lock` entries, and nothing with `--offline`, `--index-url` or a `WHEELGAP_INDEX_URL` mirror. `--notes` needs `--explain`, and `--no-notes` overrides `notes = true`. Notes that aren't in the tracker's exact format, or that could pass for a GitHub Actions workflow command, are dropped. Lookups are cached for 24 hours and capped at 15 seconds in all, stop at the first connection failure, and never change the exit status. (#255)
- The GitHub Action takes `compare-to: base` to fail a pull request only when it makes the lockfile worse: on a `pull_request` event it runs `wheelgap diff` between the base branch the pull request is merged onto (fetched if the checkout is shallow) and the merged lockfile, with `args` giving the lockfile, `-p` and `-t` (`args: uv.lock -p 3.13 -t linux-aarch64,musl-aarch64`). A git ref such as `compare-to: origin/main` works on other events. The packages and targets that got worse (`armlib 1.4.0 → 1.5.0`, `musl-aarch64`, `✓ → ● source`) and new packages with gaps go to the job summary as a table, and the new `report` output is its path. The step exits 2, never 0, when diff's exit code and report don't agree. With `comment: true` and `pull-requests: write`, the table is also posted as one pull request comment per lockfile, which every later run edits (also to say that nothing got worse, or that the check couldn't run); a read-only token, as fork and (by default) Dependabot pull requests get, leaves a warning and the summary. For a GitHub App's token, `comment-author` names the login whose comment is updated. `comment: true` is refused on `pull_request_target` and `workflow_run` events. Package names and versions are escaped in the summary and comment, and wheelgap's messages reach the log with workflow commands defused. The README's "In CI" section explains the permissions. (#253)
- `--conda-forge` adds a hint to `--explain` when conda-forge has a package with exactly the same name and a build of the same version that fits a gap's target: its Python version and ABI (free-threaded and abi3 too) and its glibc and macOS minimums (`numpy: conda-forge has a package named numpy with 2.3.4 builds for linux-ppc64le`), and `--json --explain` gives it as a `conda_forge` object. Only glibc Linux, macOS and Windows targets with a current conda-forge Python can match, and it never changes a status, the summary or the exit code. Only names known to be on PyPI go to anaconda.org: not when the input, a `uv.toml`, `pyproject.toml` or `pdm.toml` in its folder or above it, or the environment (`PIP_INDEX_URL`, `UV_INDEX` and the like) names another index; user and system pip and uv settings aren't read. Others are named in a note, runs with `--index-url` or `WHEELGAP_INDEX_URL` look nothing up, and `--offline` refuses the flag. Lookups are tried once and stop after 30 seconds, with a note when any couldn't be checked. (#254)
- Security hardening: text from a lockfile can no longer run as a GitHub Actions workflow command in a CI log. A pull request could set a package name like `::warning file=x::...` or a version containing a line break and `::error::...` or `##[...]`, and the table, `--explain`, `--markdown` and error messages printed it where the Actions runner reads commands, so it could add annotations, mask text or stop command processing. Package names in `uv.lock`, `poetry.lock`, `pdm.lock`, `pylock.toml`, `Pipfile.lock` and the PyPI packages of `pixi.lock` must now be valid PEP 508 names (anything else exits 2, naming the file; pip can't install such a name either), and everything `wheelgap` and `wheelgap diff` print goes through a guard that writes a line's leading `::` as `\u003a:` and `##[` as `\u0023#[`. In `--json` output those are JSON escapes, so the values are unchanged; normal output is never affected, and neither are the `::error`/`::warning` lines `--github-annotations` writes. Related changes: output to a pipe or file is now always UTF-8, even with `PYTHONIOENCODING` set, because the runner reads the log as UTF-8. An unexpected error is printed through the same guard and exits 2. A lockfile field of the wrong type, such as `version = 1` or a list of markers, is now an input error (exit 2) naming the file instead of a crash. Problem matchers that other steps set up with `::add-matcher::` turn ordinary lines into annotations by design, so they're out of scope. (#247)
- `pixi.lock` input: wheelgap checks the PyPI packages of a pixi environment, `default` unless `--environment NAME` picks another, and finds `pixi.lock` in a project directory when no other lockfile is there (or `--environment` is given; otherwise a note names the `pixi.lock` it passed over). `check_lockfile()` takes `environment=`. Conda packages are skipped (`conda`), counted rather than listed past five in text and Markdown output. pixi records only the one file it picked for each of the lock's platforms, so each PyPI package is also looked up on PyPI for its pinned version, and `--offline` refuses the file. A package the lock leaves out on one of its platforms, such as a Windows-only dependency, shows `n/a` on targets with that platform's markers and Python. Lock versions 6 and 7 are read; any other version, or YAML outside the plain subset pixi writes, is an error rather than a guess. The pre-commit hook runs when `pixi.lock` changes. (#251)
- `wheelgap-mcp` speaks the MCP 2026-07-28 revision as well as the `initialize` handshake of 2024-11-05 to 2025-11-25, choosing for each request: it answers `server/discover`, serves requests that carry their protocol version and capabilities in `_meta`, and answers a version it doesn't speak with error `-32022` listing the ones it does. Clients that probe with `server/discover` now stay on 2026-07-28 instead of falling back to the handshake. When a client that shares its roots passes a relative path on 2026-07-28, the server asks for them with an `input_required` result, and the path must then be in one of them (if it isn't, the call is an error saying to pass an absolute path). (#248)
- The Python API explains gaps as `--explain` does. For each `source` or `missing` target, a `Result` has `rejected` (every wheel the target can't use, and why), `reasons` (the same as text) and `via` (the dependency path that pulls the package in, such as `app → pandas → numpy`, filled by `check_lockfile()` for `uv.lock` and for `poetry.lock` before lock-version 2.1). `to_dict(explain=True)` adds `"rejected"` and `"via"` in the same shape as `--json --explain`; plain `to_dict()` is unchanged. `wheelgap-mcp`'s `check_package` tool takes `explain: true` for the same keys, with at most 8 wheels per target (`rejected_omitted` counts the rest). (#241)
- `--explain` now names a wheel that would fit but is yanked (`yanked`), where it used to say `no wheels published for this version`, when pip builds a pinned release from source because its only fitting wheel was yanked. (#241)
- `--github-annotations` marks each package with a gap on its own line of the lockfile in a pull request's diff, as a GitHub Actions annotation (`::error file=uv.lock,line=412,...`), so a dependency bump that drops a platform is flagged next to the line that bumped it. The GitHub Action turns it on. A package that fails the check is an error; a source build that `--fail-on missing` allows is a warning. `--ignore` applies, `--exit-zero` still annotates, and at most 10 of each are printed, the last one saying how many more there are. The line is found in `uv.lock`, `poetry.lock`, `pdm.lock`, `pylock.toml`, `Pipfile.lock` and requirements files (and files they include with `-r`); where it isn't certain, the annotation names the file without a line. Annotations go before the usual output, or to stderr with `--json` and `--markdown`, whose stdout is unchanged. (#244)
- `--explain` is about 2.5 times faster on big lockfiles checked on many targets (8.7 s down to 3.4 s on a laptop for 2,000 packages on `-t everything` with three Pythons): each wheel's filename is now parsed once rather than once per target, and each target's platform tags are worked out once. The results are unchanged. (#245)
- `--advisory TARGET` (or `advisory = [...]` in `[tool.wheelgap]`) reports the gaps on a platform you're watching, such as `win-arm64`, without failing the run: the column is marked `(advisory)` in the table and the Markdown report, a summary line counts those gaps, `--json` lists the targets under a new `advisory` key (`summary.per_target` still counts them), and `--junit` reports them as skipped tests rather than failures. It takes anything `-t` does, and an `--advisory` target the run doesn't check exits 2 (a configured one gets a note); a group like `all` means the checked targets among its members. `wheelgap-mcp`'s `check_lockfile` lists the advisory targets, marks each gap's `advisory_gaps`, and adds `passes`, the command line's verdict, next to `ok`. (#243)
- `-p next` and `-p next-t` (also in `[tool.wheelgap] python`, `wheelgap diff -p`, `make_targets()` and the MCP tools) check the newest CPython wheelgap knows, 3.15 in this release, and its free-threaded build, with a note on stderr saying which version that is. When exactly two Pythons are checked and one is newer, the summary names the packages that block the upgrade, those with a gap on the newer Python where the older one has a wheel (`blocking 3.15: numpy, pydantic-core`), and `--json` and the MCP `check_lockfile` tool list them as `blocking_newer_python`. Packages that couldn't be checked aren't listed, only counted. (#242)
- `wheelgap mcp` starts the MCP server, as `wheelgap-mcp` does (`--version` and `--help` too), so `uvx wheelgap mcp` works and MCP registries can start it from the `wheelgap` package. `mcp` as the first argument always starts the server, even when a file or folder named `mcp` is in the current directory (MCP clients choose that directory). To check such a folder, run `wheelgap ./mcp` or `wheelgap mcp/`; to check the PyPI package `mcp`, pin it: `wheelgap mcp==2.3.0`. Run in a terminal, `wheelgap mcp` says on stderr that it's waiting for an MCP client. (#240)

## 0.9.0 (2026-11-12)

New: an **MCP server** (`wheelgap-mcp`) so coding agents can ask wheelgap directly, with tools to check a package, a lockfile, a Dockerfile and the difference between two lockfiles ([setup for Claude Code, Cursor, VS Code, Codex and Claude Desktop](https://github.com/wheelgap/wheelgap/blob/main/docs/mcp.md)). **`wheelgap diff OLD NEW`** lists what got worse between two lockfiles, takes git refs such as `origin/main:uv.lock`, and prints `--json`. Check only what you actually install with `--extra`, `--all-extras`, `--group`, `--only-group` and `--no-dev` on `uv.lock`, and the group options on Poetry 2.x and PDM lockfiles too, with each tool's own rules. Libraries without a lockfile can check their `pyproject.toml`. Also new: `--offline` (and `offline = true`) for CI without network, `--index-url` for private indexes, `--junit` reports, requirements constraint files (`-c`), 32-bit x86 targets (`win32`, `linux-i686`, `musl-i686`), `--ignore NAME:TARGET`, a 24-hour cache of pinned lookups (`--no-cache`, `--clear-cache`), per-target counts in `--json` and `--markdown`, and a `py.typed` marker for the Python API. Some results can change on upgrade: `[tool.uv] required-environments` now sets the default targets, `-t everything` includes the 32-bit targets, version ranges respect `Requires-Python`, and `--dockerfile` now follows BuildKit's heredoc rules and rejects some images it used to guess at. 32 of the 42 changes came from 12 outside contributors.

- `pdm.lock` inputs now accept `--group`, `--only-group` and `--no-dev`, and the configured `groups`, with PDM's meanings: every group in the lock's `[metadata] groups` counts, as with a plain `pdm install` (optional-dependencies groups too, once locked with `pdm lock -G`), `--no-dev` leaves out `dev` (like `pdm install --without dev`), and `--only-group` checks only the named groups (`--only-group default` is PDM's `--prod`). A package counts if any of its groups is selected, so a production check no longer fails on a `dev`-only gap. A group that isn't in the lock is an error, with a `pdm lock -G` hint when `pyproject.toml` declares it; so are `--extra` on a `pdm.lock` and a command-line selection on a lock without package groups (locked without the `inherit_metadata` strategy), which configured `groups` leave unfiltered. (#238, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `wheelgap diff` takes a git `REF:PATH` for either lockfile, such as `wheelgap diff origin/main:uv.lock uv.lock`, so you can compare against the base branch without checking it out. It's read with git, along with the `pyproject.toml` beside it at that ref, when no file or folder of that name exists; a ref or path git can't find, or a missing `git`, exits 2 with the reason. (#237, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- The package now ships a `py.typed` marker (PEP 561), so type checkers use the Python API's annotations instead of treating `wheelgap` as untyped. (#236, thanks [@HarshRajSinghania](https://github.com/HarshRajSinghania))
- `wheelgap-mcp` accepts `file://` URIs for its path arguments (`file:///C:/...` on Windows too); any other URI scheme is a tool error. If the client declares the `roots` capability, the server asks for `roots/list` after initialization (and again when the client says the list changed) and resolves a relative path against the first root that contains it, then against its own working directory, so `uv.lock` works when the client started the server somewhere else. (#224, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `wheelgap-mcp` has a `diff_lockfiles` tool: give it the `old` and `new` lockfile (plus `python` and `targets`) and it answers as `wheelgap diff OLD NEW --json` does, with `ok` (true when nothing got worse and no new package has a gap), so an agent that bumps dependencies can check that the upgrade didn't lose a wheel. As with `wheelgap diff`, `[tool.wheelgap]` settings don't apply. (#223, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `wheelgap-mcp` has a `check_dockerfile` tool: give it a Dockerfile (and optionally the lockfile or project directory, which defaults to the Dockerfile's folder, and `targets`) and it answers as `wheelgap PATH --dockerfile DOCKERFILE --json` does, so an agent can ask before switching `python:3.13-slim` to `-alpine` or adding `--platform=linux/arm64`. The result is what `check_lockfile` returns plus `image`, the `python`, `platform`, `glibc` and `musl` wheelgap read from the final stage. A Dockerfile wheelgap can't read the way Docker does is a tool error with wheelgap's message. (#222, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `wheelgap pyproject.toml` now notes on stderr when `[project] requires-python` leaves out a Python you asked for with `-p`, and still checks that target because you asked for it. Every clause counts, as pip applies them, so `!=3.12.*` leaves out 3.12. An invalid `requires-python` is ignored with a note instead of stopping the run. `-q` drops both notes. (#221, thanks [@qiaobochi040726-source](https://github.com/qiaobochi040726-source))
- `wheelgap diff OLD NEW` runs the lockfile comparison from the main command (`python -m wheelgap.diff` still works), and `--json` prints it as one object: `worse` and `new` packages with their version lists and statuses per target, `unchecked` and `summary` counts. A file or folder named `diff` in the current directory is still read as an input, with a note, and bare `wheelgap diff` no longer checks the PyPI package of that name (pin it: `wheelgap diff==2023.12.6`). (#220)
- The cache of pinned lookups no longer grows forever: entries older than 24 hours are deleted, at most once a day (a `last-prune` file in the cache folder records when), and a failure to delete never fails a run. `--clear-cache` deletes wheelgap's entries in the `pinned-v1` folder (never anything through a link, and no other files) and says on stderr how many it removed; alone it exits 0 without checking anything, and with inputs it clears first, then checks them. (#219, thanks [@H0ozsed](https://github.com/H0ozsed))
- `wheelgap-mcp` keeps answering while a tool call runs: `ping` gets a reply during a long `check_lockfile`, a call given a `_meta.progressToken` gets `notifications/progress` as its index lookups finish, and `notifications/cancelled` stops a queued or running call's progress and result (a queued call never starts; a running one's lookups still finish before the next call). Clients that reset their timeout on progress no longer give up on a big lockfile. (#218, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `--dockerfile` now treats the control characters `\x1c`–`\x1f` as Docker does, which doesn't count them as whitespace. A line made only of them inside a continued instruction is no longer skipped as blank, so it ends the instruction as it does in Docker, and a `FROM` after it is read as a new stage instead of being joined into a `RUN`. A `FROM` with one of them in front (`\x1cFROM`) is now an error, as it is in Docker, instead of being read as a `FROM`. (#217, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `wheelgap-mcp`: `check_package` and `check_lockfile` take an optional `pyodide_lock` argument (a path or https URL of a `pyodide-lock.json`), so on `pyodide` targets the packages Pyodide ships itself, such as numpy, show as `bundled` instead of `source` or `missing`, as with `--pyodide-lock`. A lock for a Python no pyodide target uses, or one that can't be read, is a tool error. (#216, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- On `linux-armv7l` and `musl-armv7l` a `platform_machine` marker now counts as unknown, so the package is still checked: 32-bit Raspberry Pi OS on a Pi 4 or 5 boots a 64-bit kernel by default and reports `aarch64`, as can a `linux/arm/v7` container on an arm64 host, so a dependency gated on `platform_machine == "aarch64"` no longer shows `n/a` there when pip would install it. Checks on these targets may report new gaps. (#215, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- New `wheelgap-mcp` command (also `python -m wheelgap.mcp`): an MCP server over stdio, so coding agents can ask wheelgap directly. Its read-only tools are `check_package` (statuses per target for one package, with `glibc`, `musl` and `macos` arguments), `check_lockfile` (what `wheelgap PATH --json` reports, `[tool.wheelgap]` settings included: the packages with gaps, the skipped ones and any notes) and `list_targets`. Unknown argument names are errors, so a model's guessed name never silently falls back to a default. It needs only the standard library and `packaging`, and speaks the MCP revisions from 2024-11-05 to 2025-11-25; clients on newer revisions fall back to those. (#198)
- `wheelgap pyproject.toml` checks a library's direct dependencies when there's no lockfile: `[project] dependencies` are read like requirements-file lines (ranges get the newest matching release, markers are respected), and `--extra NAME` / `--all-extras` add `[project.optional-dependencies]` groups. Their own dependencies aren't checked, and a note on stderr always says so (and that ranges were checked at the newest matching release). `[dependency-groups]` isn't read yet, so `--group`, `--only-group` and `--no-dev` are errors with this input, and dynamic `dependencies` exit 2. Dynamic `optional-dependencies` with `--extra` or `--all-extras`, two extras whose names normalize to the same name (`Test` and `test`), and a Poetry project whose dependencies are in `[tool.poetry.dependencies]` rather than `[project]` are errors too. A requirement on the project itself, like `mylib[speed]`, adds that extra's requirements rather than looking `mylib` up. A directory with no lockfile but a `pyproject.toml` with `[project]` still fails, and the error now suggests `wheelgap <dir>/pyproject.toml`. `wheelgap.check_lockfile()` and `python -m wheelgap.diff` refuse a `pyproject.toml`. (#197, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- New 32-bit x86 targets: `win32` (32-bit Python on Windows), `linux-i686` and `musl-i686`, with aliases (`windows-x86`, `linux-x86`, `linux-386`, `alpine-x86`) and `linux/386` (or `linux/i386`) in `-t` and `--dockerfile`. `-t all` is unchanged, but `-t everything` now checks these three targets too, so a CI job that uses it may report new gaps. A `win_amd64` wheel doesn't count on `win32`, nor a `win32` wheel on `win-amd64`. On these targets a `platform_machine` marker counts as unknown, so the package is still checked: 32-bit Python on 64-bit Windows reports `AMD64`, and a `linux/386` container on an x86_64 host reports `x86_64`. (#195, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `poetry.lock` (Poetry 2.x) inputs now accept `--group`, `--only-group` and `--no-dev`, and the configured `groups`, with Poetry's meanings: `main` and every group not marked `optional = true` count, `--group` adds one, `--no-dev` leaves out `dev`, and `--only-group` checks only the named groups. - **PyPI lookups:** odd index responses give "unknown" instead of crashing; retries back off and honour `Retry-After`, retry dropped connections and skip permanent errors; an empty `WHEELGAP_INDEX_URL` means PyPI, and a `/simple` URL is a clear error; a missing pinned version says so ("version 1.0 not on index").
- **requirements.txt:** `-rfile` without a space, `--hash` with a space, comments after a tab, and `name@url` without spaces are all read correctly.
- **Output:** UTF-8 on Windows CI (no more "?" for ✓), `.python-version` files with a BOM, `--list-targets` uses the limits from `[tool.wheelgap]`, legacy `manylinux2014` wheels get the right `--explain` reason, more sdist formats are recognised, and `--macos 15` means 15.0.
- `--pyodide-lock`: a package whose lookup failed (e.g. a mistyped pin) was reported as bundled and could pass. It's now `unknown`, which fails.
- `pyodide-lock` in `[tool.wheelgap]` made every run without a matching Pyodide target exit 2. It's now quietly unused on those runs, and a relative path is read from the folder that holds `pyproject.toml`.
- **Yanked files:** a release pinned with `==` whose files have all been yanked was reported as having no files ("can't install"). pip still installs it (PEP 592), so its files now count, judged per target: they count only when every file that target could use is yanked.
- `pdm.lock`: packages with extras were listed twice (PDM writes one entry per extras variant). They now count once.
- The summary line could leave "unknown" packages out of its counts. Each gap package is now counted once, under its worst status.
- `quiet = true` in `[tool.wheelgap]` made `--json --explain` fail with a usage error. Quiet now only affects text output, `--no-quiet` turns it off for one run, and quiet runs still say why a package is unknown.
- `--explain`'s `via:` could credit a dependency group for a package that is also a runtime dependency. The project's own dependencies are now preferred.
- `--dockerfile` with an Alpine image plus `-t linux/arm64` checked glibc wheels. Docker platform names now keep the image's libc (musl).
- `--dockerfile`: Alpine 3.12 and earlier are checked against musl 1.1, not 1.2.
- `requirements.txt`: a bare VCS URL containing `@` (`git+ssh://git@github.com/...`) aborted the whole run. It's now skipped like other URLs.
- `python -m wheelgap.scan` now refuses to write results when more than 5% of lookups fail (`--max-error-rate`), records `lookup_errors` and each target's glibc/musl/macOS limits, and no longer counts Python 2-only wheels as "pure".

### Security

- Every GitHub Action used by wheelgap's own workflows is pinned to a full commit SHA, with Dependabot keeping the pins current, and PyPI releases now publish only from a `v*` tag through a protected environment. (#64)

## 0.1.0 (2026-11-08)

First release.

- Reads `uv.lock`, `pylock.toml` (PEP 751), `poetry.lock`, `requirements.txt` (with `-r` includes), or package names on the command line.
- Targets: `linux-x86_64`, `linux-aarch64`, `musl-x86_64`, `musl-aarch64`, `macos-arm64`, `macos-x86_64`, `win-amd64`, `win-arm64`, for any CPython version including free-threaded builds (`3.14t`).
- Evaluates environment markers and walks the `uv.lock` dependency graph per target, so Windows-only or old-Python-only packages don't show up as false gaps.
- Works offline from lockfiles that record their files; `--online` re-checks against PyPI.
- `--json` output and CI-friendly exit codes (0 clean, 1 gaps, 2 error). Also usable as a GitHub Action.
