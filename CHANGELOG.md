# Changelog

## Unreleased

- `--fix`: a hash-pinned requirements file made by `uv export` or `pdm export` is now told to upgrade its lock (`uv lock --upgrade-package NAME`, keeping the export's `--script`, `--project` or `--directory`, or `pdm update NAME`) and export again, instead of a `pip-compile` command that fails because there is no `.in` file. (#828, thanks [@mamoun123121314](https://github.com/mamoun123121314))
- A `uv.lock` whose project `[package.metadata]` has the wrong type (for example `provides-extras = [1]`, `provides-extras = "abc"`, `requires-dev = []` or `metadata = []`) now stops with a clear error naming the file, package and field (exit 2, and an error object with `--json`) before any index lookup, instead of an `AttributeError` or a silently misread value (`"abc"` was read as the extras `a`, `b` and `c`). (#805, thanks [@Mugunth007](https://github.com/Mugunth007))
- `--dockerfile-inputs`: the npm pass-over for a local `npm install` of named packages now also looks at earlier `RUN` lines, not only `COPY` and `ADD`: a command wheelgap doesn't read that may write the install's folder or a folder above it (`git clone URL`, with or without a folder, `tar xf web.tar -C /srv`), names a `package.json` (`printf '{}' > /app/package.json`, `touch package.json`, `wget URL/package.json`), names a path with a variable wheelgap can't resolve, or is a heredoc script keeps the warning, and the stop under `--deps`. A `mkdir` of the folder itself still passes over. (#842, thanks [@jay23606](https://github.com/jay23606))
- `--dockerfile-inputs`: a `UV_*` setting whose value uv refuses (`ENV UV_LINK_MODE=bogus`, `UV_NO_CACHE=maybe`, `UV_HTTP_TIMEOUT=abc`), set by `ENV`, `ARG` or on the `RUN` line, now refuses the `uv pip install` or `uv sync` line that reads it, with a message naming the setting, the value and the values uv takes. uv exits 2 on such a value, but the line was read as if it would install. pip doesn't read these settings, so a `pip install` line is still read, and `ENV UV_SYSTEM_PYTHON=yes` (or any other spelling uv takes as true) now counts as `--system`, as uv reads it. (#841, thanks [@jay23606](https://github.com/jay23606))
- `--fix --build-info`: a gap with no fix on a Linux target that builds from source now says which distro packages its build needs, from the sdist's `[build-system]` requires: `apk add --no-cache build-base`, `cmake` or `cargo` on Alpine for `musl-*` targets, `apt-get update && apt-get install -y build-essential`, `cmake` or `cargo` on Debian or Ubuntu for `linux-*` targets, with `python3-dev` for the distro's own Python. `--json --fix` gives the same as `build_packages` in each `none` entry, and the MCP `explain_install_failure` tool returns it with `build_info: true`. These are build tools only: a library the package links against, such as libxml2 for lxml or BLAS, isn't named. Only the sdists of gaps with no fix are downloaded. (#814)
- Requirements files and `pyproject.toml`: a package required twice (in a file and a `-r` file, on two lines, or in `dependencies` and a selected extra) is now checked as pip and uv install it: one release that every line whose marker holds allows. Before, each line was its own row, so `numpy==1.26.4` in `base.txt` with `numpy>=1.20` also showed numpy 2.5.5, a release pip never installs. Ranges are intersected; lines no release satisfies together (`numpy==2.3.0` and `numpy<2`, `numpy>=2` and `numpy<2`) are `unknown`, as pip refuses them; and lines under different markers are decided per target with the lines that hold there (`numpy>=1.20` and `numpy<2; sys_platform == "win32"` is merged on Windows only), with a target `unknown` only where a marker it can't decide could change the release. Such a name counts as one package in the header and in `--json`'s `summary.packages`. (#835)
- Requirements files: a requirement whose `--hash` values are all sha384 or sha512 is now `unknown`, with a reason naming the line. Before, those hashes were dropped, which turned hash checking off: `markupsafe==3.0.2 --hash=sha512:<the sdist's>` was a `wheel` on macOS arm64, where pip picks the wheel and refuses it on the hash mismatch. PyPI gives sha256 digests only. Beside sha256 values, they make only the targets where no file with a listed sha256 fits `unknown`. (#835)
- Requirements files: a `-c` constraints file given by URL (`-c https://releases.openstack.org/constraints/upper/2023.1`) or through an environment variable (`-c ${PIP_CONSTRAINT}`) is now an input error naming the file and line. Before, it was skipped without a note, and the packages it constrains were checked at their newest release: pip applies the file, so `numpy` under the openstack constraints installs numpy 1.23.3, which has no Python 3.13 wheel, while wheelgap said `wheel`. Abbreviations pip accepts (`--cons FILE`, `--requirem FILE`) are now followed like the full options, and `--req`, which pip refuses as ambiguous, is an input error. (#835)
- `--fix --deps` no longer says "In --deps, change the pins to ...": a direct requirement keeps its own file and range, so `numpy<1.25` in requirements.txt gets "needs requirements.txt's numpy<1.25 relaxed" and "In requirements.txt, change the requirements to numpy==1.26.0", as without `--deps`. When another package in the resolved tree requires a range that rules the newer release out, there's no pin to write, whether the package is a direct requirement or not: `oldest-supported-numpy==2023.12.21` requires `numpy==1.23.2` on Python 3.11, so "Use numpy==2.3.0" had no solution, and `streamlit==1.28.0` requires `numpy<2`. Such a gap goes under "No fix yet", naming only the packages whose requirement rules the release out, with the new `--json` reason `held_back`. A dependency held back only by a `-c` constraint or `exclude-newer` gets the upgrade with what to relax or move, and no line of its own to edit. (#833)
- `--fix` and `--suggest` now apply uv's `exclude-newer` cutoff (a uv.lock's `[options]`, including `exclude-newer-package` and a duration, or a `pyproject.toml`'s or script's own setting) when they look for a newer release, as `uv lock` does. A release uploaded after the cutoff was named as if `uv lock --upgrade-package` could reach it: numpy 2.1.0 for a lock with `exclude-newer = "2024-08-01T00:00:00Z"`, where uv picks 2.0.1, which still builds from source on Python 3.13. When only such a release has the wheel, the line now says it `needs uv's exclude-newer moved past` the time its last file was uploaded, the what-to-run lines start with moving it, and `--json`'s upgrade fix has a new `exclude_newer` key. For a duration (`exclude-newer = "850 days"`, which uv records as `exclude-newer-span`, or per package as `{ timestamp = ..., span = "P850D" }`), the line names the duration to shorten instead of the time it gives this run. A package whose cutoff wheelgap can't read from the lock isn't looked up. (#833)
- `--fix` on a uv.lock now reads each of the project's requirements for a package only where its marker holds on the target: with `numpy<2; python_version<'3.13'` and `numpy>=1.26; python_version>='3.13'`, a 3.13 upgrade to 2.1.0 is within your constraint, not "needs pyproject.toml's numpy<2 relaxed", and such a requirement no longer turns a "Maybe, with uv" gap into "No fix yet". An `extra == ...` marker counts as holding, since uv locks every extra; when a marker can't be decided on the target, nothing is said about the constraint. Targets whose requirements differ get a line each. (#833)
- `--fix` and `--suggest` no longer move a pre-release pin to the next pre-release when a final release has the wheel: `greenlet==2.0.0rc5` on Python 3.12 now gets 3.0.0, not 3.0.0a1, and `grpcio==1.58.0rc1` gets 1.59.0, not 1.59.0rc1. For a pre-release pin, wheelgap now names one final release for every target, else one pre-release for every target, else a final release where one fits and a pre-release for the rest. A pre-release is labelled as one in the text, Markdown, annotation and `compare-to` comment output, and by the new `prerelease` key of `--json`'s upgrade fix. (#833)
- A `pdm.lock` made for some targets only (`pdm lock --platform`, `--python` or `--implementation`, recorded as `[[metadata.targets]]`) now covers just those, as for a `uv.lock` with `[tool.uv] environments`: a target outside them is an error naming the targets it does cover, and the default platforms are narrowed to those, instead of false `source` gaps on platforms the lock left out and `pdm install` refuses. In `wheelgap diff`, a Python the targets leave out isn't compared, with a note, as for a `uv.lock`'s `requires-python`. (#832, thanks [@patrickballard](https://github.com/patrickballard))
- A Poetry 1.x `poetry.lock` (lock-version before 2.1) checked without a `pyproject.toml` beside it that declares the project's dependencies (missing, unreadable, or declaring none) no longer hides a direct dependency that another package needs only under a marker: where no dependency installs a package on a target and it has no wheel there, it is now `unknown` there (with the reason under `--explain`, in a new `unknown_reasons` key in `--json` and `Result.unknown_reasons`, and a note), since Poetry installs a direct dependency everywhere. It used to be hidden with no note. (#832, thanks [@patrickballard](https://github.com/patrickballard))
- A `poetry.lock` package with `files = []` is now looked up on its index, as Poetry installs it, instead of showing `✗ missing`; one from another index is skipped as `private index`. (#832, thanks [@patrickballard](https://github.com/patrickballard))
- `pyproject.toml` and `# /// script` inputs follow `[tool.uv.sources]`: a git, URL, path or workspace source is skipped instead of checked on PyPI, an `index` source takes the package from that index, and a source by marker, extra or group is `unknown`; a package without a source is no longer looked up on PyPI when the uv settings name another index (it's skipped as a private index, or `unknown`). They also apply uv's `no-build`, `no-binary`, `no-build-package` and `no-binary-package`, as a `uv.lock` does, and every input now lets a package list override the other kind's blanket setting, as uv does. A `uv.lock` now reads those settings from a `uv.toml` or `[tool.uv]` in a folder above it, as `uv sync` does, and a script's lock applies its script's and the folders' settings as `uv run` does instead of refusing them. A first `pyproject.toml` above a project that doesn't parse, which stops `uv sync`, is now an input error. (#834)
- `scripts/check_projects.py`, the referee check for whole projects, now compares `poetry.lock` inputs too: a pinned Poetry exports the lock offline (it reads only the lock and `pyproject.toml`, and nothing of the project runs), and `uv pip compile` answers for every exported pin on each target, for wheelgap's default and for a plain `poetry install`. (#829, thanks [@patrickballard](https://github.com/patrickballard))

Those targets get a note, a new `not_compared` key in `--json` and a "Not compared" line in the job summary and comment, and never count as worse; the last line then says "Nothing got worse on the compared targets." ## 0.14.0 (2026-11-24)

**`--fix` now says how to close each gap.** For each package that would build from source, it names the nearest newer official release that has the wheel, and what to run for your input: `uv lock --upgrade-package NAME` for a `uv.lock`, the new pin for a requirements file. Where no release has the wheel, or if you can't upgrade, it offers an unofficial wheel from wheelgap's [gap wheel index](https://wheelgap.github.io/wheels/), built by wheelgap from the PyPI sdist, not by the package's maintainers. In 83 pinned projects from the 300 most-starred Python repositories, 82% of the Python 3.15 gaps on Linux x86-64 were stale pins of this kind: the release with the wheel was already out. The upgrade lookups send the gap packages' names to pypi.org, as `--suggest` does, and only for packages positively from PyPI. `--json` adds each package's `fix` and a `fix_summary`, and the MCP tools `check_lockfile` and `check_dockerfile` take `fix: true`.

**Answers follow pip and uv more closely.** Requirements files are read as pip reads them (`--pre`, `--all-releases`, `--only-final`, `--hash`, constraints that conflict, includes, and a note for an index option wheelgap doesn't read). **`--dockerfile-inputs`** checks the requirements files a Dockerfile's final stage installs, through its base stages, `-r`/`-c` includes and `.dockerignore`, reading the files of one `pip install` line together as pip does, and says when a `RUN` line runs the project's own code (`npm ci`, `cargo build`, a script) that wheelgap can't see into.

**New inputs:** a script's `# /// script` block and its `uv lock --script` lock, a conda `environment.yml`, `pyproject.toml` dependency groups, and a project folder with no lockfile at its root.

**Also:** GitLab Code Quality reports, `.gitlab-ci.yml` in `--suggest-targets`, `--piwheels`, `wheelgap diff --deps`, and the MCP tools `explain_install_failure` and `suggest_targets`.

- `--dockerfile`: Alpine 3.12 and earlier are checked against musl 1.1, not 1.2.
- `requirements.txt`: a bare VCS URL containing `@` (`git+ssh://git@github.com/...`) aborted the whole run. It's now skipped like other URLs.

- Support `pdm.lock` inputs, reading the distribution filenames and package markers recorded in the lockfile so PDM projects can be checked offline. Entries without a files list are looked up on PyPI. (#36, thanks [@draarivpatel-ui](https://github.com/draarivpatel-ui))
- Without `-p`, the Python versions come from a `.python-version` file next to the lockfile (or `pyproject.toml`) before falling back to the running Python. `-p`, `--dockerfile` and `[tool.wheelgap]` still win. ## 0.1.0 (2026-11-08)

First release.

- Reads `uv.lock`, `pylock.toml` (PEP 751), `poetry.lock`, `requirements.txt` (with `-r` includes), or package names on the command line.
- Targets: `linux-x86_64`, `linux-aarch64`, `musl-x86_64`, `musl-aarch64`, `macos-arm64`, `macos-x86_64`, `win-amd64`, `win-arm64`, for any CPython version including free-threaded builds (`3.14t`).
- Evaluates environment markers and walks the `uv.lock` dependency graph per target, so Windows-only or old-Python-only packages don't show up as false gaps.
- Works offline from lockfiles that record their files; `--online` re-checks against PyPI.
- `--json` output and CI-friendly exit codes (0 clean, 1 gaps, 2 error). Also usable as a GitHub Action.
