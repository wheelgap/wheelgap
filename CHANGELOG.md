# Changelog

## Unreleased

- With `--deps`, a transitive package that couldn't be checked (its lookup failed, no release matches, or it's a direct URL) now names the direct requirement that brings it in (`flaky (via usesflaky)`), in the text and Markdown tables, `--junit` and the GitHub annotations. (#479, thanks [@patrickballard](https://github.com/patrickballard))
- `--explain --fix` adds a `gap wheel` line under a package that a wheel on the gap wheel index fills: unofficial, built by wheelgap from the PyPI sdist; not from the package's maintainers. It gives the `pip install` command for inputs pip installs from as they are, and points to the `--fix` section for lockfiles. `--json --explain --fix` adds a `gap_wheel` object per package. The validated list is now cached for 24 hours, with plain `--fix` too (`--no-cache` skips it). It never changes results or exit codes. (#477, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- Python API: `check_lockfile(..., deps=True)` raises `SourceError` naming any requirement that isn't an index package (`-e .`, a path, a URL), since what it installs isn't checked; pass `allow_skipped=True` to check the rest, as 0.13.0 did. A requirements file compiled with hashes is still checked as written. (#476, thanks [@dianatofficial](https://github.com/dianatofficial))
- With `--extra` or `--all-extras` on a poetry.lock, a package that a selected extra already installs no longer gets the "kept for every extra" note when another of its groups has a platform marker. (#475, thanks [@patrickballard](https://github.com/patrickballard))
- `wheelgap diff PKG==OLD PKG==NEW --deps` resolves both releases' dependency trees from PyPI per target and compares them as it compares two lockfiles. (#474, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `wheelgap diff` names the direct dependency that brings in a new or worse transitive gap (`cryptography (via mcp) 50.0.2 (new)`), in the text report and the Action's PR comment, and `--json` adds `direct` per target. (#473, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--fix` lists the gaps a wheel on wheelgap's [gap wheel index](https://wheelgap.github.io/wheels/) fills, with how to install it: a `pyproject.toml` snippet for a uv.lock (and which packages to also list as direct dependencies, since uv applies `[tool.uv.sources]` only to direct ones), or the `--extra-index-url` line for pip. Only for packages positively from PyPI, exactly the checked version and a wheel the target accepts; it reads the list in one request that names no package, and never changes the exit code. `--json` gets a `gap_wheels` key. (#472, thanks [@patrickballard](https://github.com/patrickballard))
- `--explain` can infer issue links from Codeberg and GitLab repository URLs, skipping site pages such as `gitlab.com/explore/projects`; a nested GitLab project is linked only when its URL has the `/-/` part that marks where the project path ends. A source URL with `..`, `%` or `\` in its path no longer gives a link on any host. (#470, thanks [@Gorkem-Taha](https://github.com/Gorkem-Taha))
- SARIF gap messages name the direct dependency that brings in a transitive package, per target (`cryptography 50.0.2 (via mcp) builds from source on win-arm64.`), as `--junit` does. (#469, thanks [@CyberKun](https://github.com/CyberKun))
- `--no-build-info` turns off `build-info = true` from `[tool.wheelgap]` for one run, and MCP `check_lockfile` with `dependencies: true` passes `--no-build-info` so it never downloads sdists. (#465, thanks [@gouthm04](https://github.com/gouthm04))
- `--explain` no longer turns GitHub pages such as sponsors and organization projects into issue tracker links. (#457, thanks [@Vietpr](https://github.com/Vietpr))
- MCP tools keep their `notes` when `FORCE_COLOR` is set: the CLI now always runs with `--color=never`, so a dimmed note's ANSI prefix no longer hides the `wheelgap: note:` marker and gets the note dropped. (#456, thanks [@P-r-e-m-i-u-m](https://github.com/P-r-e-m-i-u-m))
- `--dist` with `offline = true` in `[tool.wheelgap]` now names the real way out — set `offline = false` in `[tool.wheelgap]` (or drop the key) — instead of telling you to pass `--online`, which `--dist` refuses. (#452, thanks [@Seyamalam](https://github.com/Seyamalam))

## 0.13.0 (2026-11-16)

New: **`--from-log FILE`** turns a failed `pip install` or uv install log into the answer: the packages that failed to build, why no wheel fits the Python and platform you name, and the release that has one. wheelgap also reads a **pip installation report** (`pip install --dry-run --report`), so it checks exactly what pip resolved on a machine without installing anything, and **`--sarif PATH`** puts each gap in GitHub code scanning at its lockfile line. For agents and scripts, the MCP server gains **`check_dist`** (the `--dist` release gate as a tool), `check_package` gives the whole way out for a pinned version and every package in its tree, `check_lockfile` takes `dependencies: true` for a requirements file or `pyproject.toml`, and the Python API's `check_lockfile(..., deps=True)` does the same. The direct dependency behind a transitive gap is now in `--json --explain` and the API (`direct`), in `--junit` messages, and on the right requirement line with `--deps --github-annotations`. 14 of the 15 changes came from 6 outside contributors.

Upgrade note: statuses and exit codes don't change, except that `--deps` with a constraint file that has environment markers (OpenStack's upper-constraints, say) is now checked instead of refused, and `--explain` no longer crashes on a project URL Python can't parse. Output can change: `--junit` failure and advisory-skip messages add `(via …)` for a transitive gap, and the element's text a `Direct dependencies:` line (testcase names don't change); `--deps --github-annotations` puts annotations on requirement lines again, or names the file alone when no line is certain, and names what pulls a transitive gap in. JSON keys are only added.

- `--deps --github-annotations` on a requirements file puts each annotation back on a line: a direct requirement's gap is on its own line again, and a transitive gap is on the line of the requirement that pulls it in when that's unambiguous, with the message naming what pulls it in (`(via mcp)`), as the table does. More than one puller stays file-only rather than guess a line. (#446, thanks [@Seyamalam](https://github.com/Seyamalam))
- Python API: `check_lockfile()` takes `deps=True` to check everything a requirements file or `pyproject.toml` installs, resolved per target from PyPI metadata as `--deps` does. Each package in the tree gets a `Result` with `via` and `direct`, `pyproject.toml` (and project directories containing only one) is accepted, and it's refused where `--deps` refuses (lockfiles, `offline=True`, another index). (#445, thanks [@dianatofficial](https://github.com/dianatofficial))
- MCP `check_lockfile` now accepts `dependencies: true` to check the complete dependency tree of requirements files and `pyproject.toml`, reporting transitive dependency origins and rejecting unsupported inputs rather than silently checking only direct requirements. (#443, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- MCP's `check_package` now gives the full way out `--explain --suggest` reports: `suggest` names, per gap target, the newer release that has the wheel (next to `last_with_wheel` for targets no newer release covers), and with `dependencies: true` each `dependency_gaps` entry gets its own `suggest` and `last_with_wheel` — one batched lookup for the whole tree, and a failed lookup leaves the keys out rather than guess. (#442, thanks [@Seyamalam](https://github.com/Seyamalam))
- `--junit`: a transitive gap's failure or advisory-skip message names the direct dependency that pulls it in on that target, as the tables do (`source (via mcp)`), and its text lists them all; testcase names don't change. (#444, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- The MCP server gains `check_dist`: the `--dist DIR` release check as a tool, for the wheels and sdist about to be uploaded. It returns the per-target answer plus `dropped` — each target the newest older PyPI release had a wheel for that this one doesn't — and `ok` is false when anything was dropped, when a target has no wheel, or when the comparison couldn't run, rather than a guess. `path` takes the same forms as the other tools (absolute, `file://`, or relative to a client root), and `[tool.wheelgap]` settings come from the nearest folder above it with a `pyproject.toml`, not the server's working directory. (#439, thanks [@Seyamalam](https://github.com/Seyamalam))
- `--explain` no longer crashes when a package's project URLs include one Python can't parse, such as `https://[github.com/...`: that URL is skipped and the next label or the GitHub fallback is used. (#440)
- `--from-log FILE` (or `-` for stdin) turns a failed `pip install` or uv install log into the answer: it finds the packages that failed to build and checks each with `--explain --suggest` for the Python and platform you name with `-p` and `-t`, or with `--dockerfile` for a docker build (one or the other is required, as the log doesn't say where it ran), so you see why no wheel fits and the release that has one. The version comes from the log; a failure it can't read, a version the log doesn't give (a local project's `Processing`, `pip install -q`) or leaves unclear (more than one, or pip backtracked), or a log that used another index than PyPI or `--find-links`, is an error rather than a guess. pip 25.2's new form of the summary (`× Failed to build installable wheels ...`) is read too. Logs copied from GitHub Actions (timestamps, colour) and saved by PowerShell (UTF-16) work too. (#424, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--sarif PATH` also writes a SARIF 2.1.0 report for GitHub code scanning: one result per package and gap target (`wheelgap/source` or `wheelgap/missing`), at the package's line in its lockfile, with the `--explain` reason in the message. The level is `note` on an `--advisory` target and `warning` for a source build `--fail-on missing` allows; `--ignore NAME:TARGET` gaps are left out. [CI](https://wheelgap.github.io/wheelgap/ci/#code-scanning) has an upload-sarif workflow. (#430, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- Python API & MCP: `Result.to_dict(explain=True)` and MCP's `check_package` (with `explain: true`) now include `issues_url`, the package's issue tracker link from PyPI metadata, matching `--json --explain`. In the Python API, `Result.issues_url` is also accessible directly, and `dependency_gaps` in MCP includes `issues_url` when `dependencies: true` and `explain: true` are combined. (#429, thanks [@dianatofficial](https://github.com/dianatofficial))
- The Python API's `Result` now carries `direct`: for each gap target, the direct dependencies that lead to it (`Row.direct_via`), and `Result.to_dict(explain=True)` adds `direct` mirroring `wheelgap --json --explain`. (#431, thanks [@Himanshu-Sharma12](https://github.com/Himanshu-Sharma12))
- `--deps` on a requirements file no longer refuses a constraint file with environment markers (`urllib3<2; python_version < "3.10"`), such as OpenStack's upper-constraints: each marked constraint applies on the targets where pip would apply it, and `extra == "..."` never holds on a constraint, as in pip. A marker a target can't decide (`platform_release`, `platform_version`, or `platform_machine` on a target like `linux-armv7l`) on a package the tree installs still stops the run with an error, as a URL constraint does. (#425, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--json --explain` adds `direct` to each package: for each gap target, the direct dependencies that lead to it (`{"win-arm64": ["mcp", "httpx"]}`), as the text table's `cryptography (via mcp)` names them, for uv.lock, Poetry 1.x and `--deps` inputs. Additive: `{}` for a direct dependency or an input without a graph, and no existing key changes. (#427, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- wheelgap now reads a pip installation report (`pip install --dry-run --report report.json`) and checks exactly the packages pip resolved, without installing them. A report holds what pip resolved for the machine it ran on, so wheelgap checks it only on that target (same platform, machine, Python and implementation) and refuses any other, since another target can install other packages. Packages pip didn't get from PyPI (VCS checkouts, local paths, direct URLs, another index) are skipped, and a report whose packages all came from a mirror such as Artifactory or devpi is an error, not an empty pass. (#423, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--deps --explain` reads each shared package's requirements once per target when it works out which direct dependency leads to a gap, rather than once per direct dependency, so big trees answer faster. (#420, thanks [@Gorkem-Taha](https://github.com/Gorkem-Taha))

## 0.12.0 (2026-11-16)

New: **`--deps --explain`** now gives the way out by default: each gap ends with the nearest newer release that has the wheel, or the last older one that did, and `--deps` works on requirements files and `pyproject.toml` as well as package names. Gap tables name the direct dependency behind a transitive gap (`cryptography (via mcp)`), and `--explain` links each gap to the package's issue tracker (`ask for a wheel: <url>`). For maintainers, the Action's **`dist`** input is a release gate: it runs the new **`--dist DIR`** on the files about to be uploaded and fails the job, before the upload step, when they drop a platform the previous release on PyPI had a wheel for. **`--write-constraints FILE`** writes `--suggest`'s answers as a pip/uv constraints file. Also: `--badge PATH` for a README badge, `--build-arg` for a Dockerfile's ARG values, the way out in the Action's pull request comment, `dependencies: true` and `last_with_wheel` in the MCP server's `check_package`, `deps=True` in the Python API, and an on-disk cache for `--deps`.

Output can change on upgrade, and so can results for one case: with `--deps`, a requirements file or `pyproject.toml` given next to package names now has its whole tree checked, where 0.11.0 checked only its direct requirements. Otherwise statuses and exit codes don't change: text and Markdown gap tables add `(via …)` to a transitive gap's name, `--explain` adds an `ask for a wheel:` line (and `--json --explain` an `issues_url` key), and `--deps --explain` now looks up and prints suggestions unless you pass `--no-suggest`.

- `--explain`'s issue tracker link now also finds labels spelled `Issue-Tracker`, `Bug-Tracker`, `bugtracker`, `issue_tracker` or `GitHub: issues`: `project_urls` labels are normalised as PyPI normalises its well-known labels (PEP 753) before matching. A label that only contains "issues", such as `Known issues`, still doesn't count. (#417, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `--deps` now caches each wheel's metadata file (its `Requires-Dist`) on disk for 24 hours, like pinned lookups, so a repeat run asks PyPI only for the release lists. `--no-cache` skips it, `--online` asks again, failed reads aren't cached, and the Python API doesn't use it. (#408, thanks [@sarankumar1325](https://github.com/sarankumar1325))
- `--explain` now links each gap to the package's issue tracker from PyPI metadata (`ask for a wheel: <url>`), only for packages whose index is known to be PyPI. `--json --explain` includes an additive `issues_url` per package. (#407, thanks [@dianatofficial](https://github.com/dianatofficial))
- Text and Markdown gap tables now name the direct dependency behind a transitive gap (for example, `cryptography (via mcp)`), with a count when more direct dependencies lead to it; works with `uv.lock`, Poetry 1.x and `--deps`, while leaving JSON and quiet output unchanged. (#406, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- Action: a `dist` input runs `--dist` on the folder about to be uploaded, as the release gate in docs/ci.md: the job fails when the release drops a platform the previous release had a wheel for, so the upload step never runs. It can't be combined with `compare-to`. (#405, thanks [@Seyamalam](https://github.com/Seyamalam))
- `--deps --explain` now runs `--suggest` by default, since `--deps` already looks every package in the tree up on PyPI: each gap ends with the way out, the nearest newer release with the wheel or the last older one that had it. `--no-suggest` turns it off; when an input isn't one `--deps` resolved (a lockfile, an already-pinned file), and with every other input, `--suggest` stays opt-in. (#404, thanks [@kushaldave002](https://github.com/kushaldave002))
- `--build-arg NAME=VALUE` (repeatable, with `--dockerfile`) gives a global ARG the value `docker build --build-arg` would: it replaces the ARG's default, or gives one with none a value, under the same rules as defaults. A name no ARG before the first `FROM` declares is ignored with a note, as Docker ignores it there, and the note says which values came from `--build-arg` and which were defaults. MCP: `check_dockerfile` takes the same values as `build_args`. (#393, thanks [@kushaldave002](https://github.com/kushaldave002))
- `--dist DIR` checks the wheels and sdist a release is about to upload: per target, whether a wheel installs or the sdist builds, plus a `had a wheel, this release has none` line — and a failing exit — for every target the previous release on PyPI (the newest one older than this) had an installable wheel for that these files drop. `--ignore`d and `--advisory` targets don't count. (#391, thanks [@Seyamalam](https://github.com/Seyamalam))
- `--write-constraints FILE` (with `--explain --suggest`) writes `--suggest`'s answers as a pip/uv constraints file, one pin per package: `cryptography==46.0.3  # wheels for win-arm64; 50.0.2 has none`. A package is pinned only when one release covers the gap targets `--suggest` named one for without dropping a wheel it has elsewhere; the others are left out with a comment saying why. The file isn't checked against the rest of the tree: `pip install -c FILE ...` or `uv pip compile -c FILE ...` checks it. (#392, thanks [@kushaldave002](https://github.com/kushaldave002))
- MCP: `check_package` takes `dependencies: true` to also check everything the package installs, resolved as `--deps` does: `dependency_gaps` lists each package in the tree with a gap, with its `results`, `gaps` and `via` path (`mcp → PyJWT → cryptography`), `dependencies_checked` counts the packages checked, and `ok` covers the whole tree. (#390, thanks [@kushaldave002](https://github.com/kushaldave002))
- Action: with `compare-to` and `comment: true`, the pull request comment now gives the way out under each package that got worse, from `--explain --suggest`: the nearest newer release that brings the wheels back, or the last older one that had them. Lookups are only for packages known to come from PyPI, and a failed one leaves the comment and the result as they were. (#389, thanks [@Golden007-prog](https://github.com/Golden007-prog))
- `--deps` now also works on requirements files: each requirement line is a root, markers and extras and `-c` constraints apply, `--no-binary` and `--only-binary` reach the resolved packages, and the whole tree the file installs is checked per target. A fully pinned `pip-compile` file (every requirement pinned, with `--hash` lines or `# via` comments) is checked as written, with a note. (#387, thanks [@Seyamalam](https://github.com/Seyamalam))
- `--deps` also resolves the transitive dependencies of a `pyproject.toml`, including selected extras and target-specific markers. (#386, thanks [@Golden007-prog](https://github.com/Golden007-prog))
- `--badge PATH` writes a [shields.io endpoint](https://shields.io/badges/endpoint-badge) file with how many of the checked targets have wheels for everything, such as `7/8 targets`: a target counts when nothing on it is `source` or `missing`, and any `unknown` result makes it `unknown`. It's written even when the check fails, so CI can publish it; docs/recipes.md shows a README badge from GitHub Pages. (#385, thanks [@kushaldave002](https://github.com/kushaldave002))
- Python API: `check_packages()` and `check_package()` take `deps=True` to also check everything the packages install, resolved for each target from PyPI's metadata as `--deps` does: a `Result` for every package in the tree, with `via` giving each gap's path (`mcp → PyJWT → cryptography`), and the same `DepsError` when the tree can't be settled. `check_package(deps=True)` returns a list. (#383, thanks [@kushaldave002](https://github.com/kushaldave002))
- MCP: `check_package` now returns `last_with_wheel`, as `--explain --suggest --json` does: for each gap target no newer release has a wheel for, the newest older release that has one, so an agent can say which version to pin. (#373, thanks [@kushaldave002](https://github.com/kushaldave002))
- `--dockerfile`: a global `ARG` for a name BuildKit sets itself (`TARGETARCH`, `TARGETPLATFORM`, `BUILDPLATFORM` and the rest) with no default now says the value is set by the build, not that a `--build-arg` value isn't read. One with a default is still used as BuildKit does: the default replaces the automatic value. (#371, thanks [@kushaldave002](https://github.com/kushaldave002))

## 0.11.0 (2026-11-15)

New: **`--deps`** checks everything that package names on the command line install, resolved for each target from PyPI's metadata, with the path to each gap: `wheelgap mcp==2.3.0 --deps -t win-arm64 --explain` finds that cryptography builds from source there, `via: mcp → PyJWT → cryptography`. And when no newer release has a wheel for a gap, **`--explain --suggest`** now names the last older one that did (`the last one that did is 46.0.3`). `--explain --notes` also shows the [coverage tracker](https://wheelgap.github.io/tracker/)'s build lab results; uv.lock inputs follow `[tool.uv]` `no-build` and `no-binary` and match top-level requirements by their source; and the MCP server's `check_lockfile` takes a pixi `environment`, while `check_dockerfile` reports the `build_args` it used.

Some results can change on upgrade: a uv.lock project with `no-build` or `no-binary` in `[tool.uv]` or `uv.toml` now gets `missing` or `source` where uv does, two top-level uv.lock requirements of one name and version from different indexes now each count only where uv installs them, and the Python API's `bundled_version` is `None` when the Pyodide locks checked bundle different versions.

- `--explain --suggest`: when no newer release has a wheel for a gap target, the line now names the newest older release that did, such as `cryptography 50.0.2: no newer release has a wheel for win-arm64; the last one that did is 46.0.3`, so you know which pin avoids the build. It reads the 50 releases before the checked one, counted as for newer ones (not yanked, installable on that target and Python, no pre-release unless the checked version is one). `--json` adds a `last_with_wheel` object next to `suggest`. (#367, thanks [@kushaldave002](https://github.com/kushaldave002))
- uv.lock: `no-build`, `no-build-package`, `no-binary` and `no-binary-package` from `[tool.uv]` (or `uv.toml` beside it, which uv reads instead) now apply to the lock's index packages as `uv sync` applies them: a package that may not be built is `missing` rather than `source` when it has no fitting wheel, one that may not use wheels is `source`, and `--explain` names the setting. `wheelgap diff` with a git ref (and the Action's `compare-to`) reads that ref's `uv.toml` beside the lock too, as it already did its `pyproject.toml`. A value of the wrong type is an input error. (#365, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--deps`: for package names on the command line, also check everything they install, resolved for each target from PyPI's metadata, with markers and extras followed as pip evaluates them there. `wheelgap mcp==2.3.0 --deps -t win-arm64 --explain` finds that cryptography builds from source, `via: mcp → PyJWT → cryptography`. It takes the newest release meeting every constraint, supporting the target's Python and not yanked; when constraints only a backtracking resolver could untangle come up it stops with an error instead of guessing, and a release whose dependencies it can't read is `unknown`. It agrees with `uv pip compile` on the trees of 14 popular packages on Windows on ARM and Linux. Not with `--offline`, `--index-url` or lockfile inputs. (#353, thanks [@patrickballard](https://github.com/patrickballard))
- uv.lock: a top-level requirement in `[manifest] requirements` (a `uv lock --script` lock) or `[manifest.dependency-groups]` (a virtual workspace) now counts only the package from the source it names, so two entries with the same name and version from different indexes (torch from the PyTorch CPU index on Linux, from PyPI elsewhere) each count only where uv installs them, as #299 did for package dependencies. A git requirement matches the locked package whatever commit it resolved to, and a source key of the wrong type, or two sources on one requirement, is an input error. (#363, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- MCP: `check_dockerfile`'s `image` now has `build_args`, the global `ARG` defaults its `FROM` used (`{}` when none), and its note about them says to use `check_lockfile` with `python` and `targets` if the build sets `--build-arg`, instead of the command line's `-p/-t` advice. (#348, thanks [@AdityaSreevatsaK](https://github.com/AdityaSreevatsaK))
- `--explain --suggest` now formats suggestions as a Markdown list when combined with `--markdown`, placed below the `<details>` block for rejected wheels. (`--markdown --suggest` without `--explain` remains an error.) (#347, thanks [@dianatofficial](https://github.com/dianatofficial))
- MCP `check_lockfile` accepts an `environment` argument to check a named pixi environment instead of `default`. Unknown environment errors list the names in the lockfile. (#344, thanks [@MAD1IZJOD](https://github.com/MAD1IZJOD))
- `--explain --notes` now also shows the [coverage tracker](https://wheelgap.github.io/tracker/)'s build lab results for a `source` cell, from the same file as the notes: whether exactly that release built from its sdist for exactly that target on GitHub's runners, and imported, such as `pkg 1.0 on win-arm64: build lab (2026-11-15, windows-11-arm, Python 3.14.2): builds from source in 87 s and imports`, `... but importing it turns the GIL back on` or `fails to build: needs a Rust toolchain`. A wheel with no compiled extension module is never shown as a working build, and a result for another release shows nothing. These are the lab's dated observations on its runners, not a promise about your machine, and nothing it built is downloaded. `--json --explain` adds a `build_lab` object to each package, keyed by target label, with each result's fields and `verdict`. (#338, thanks [@patrickballard](https://github.com/patrickballard))
- `--suggest-targets` now reads a GitHub Actions job's `container:` when it names a single literal image (as a string, or `container.image`), with `dockerfile.parse_image` the same way a Dockerfile's `FROM` is read: `container: python:3.13-alpine` on `ubuntu-latest` suggests `musl-x86_64`, Python 3.13 and `musl = "1.2"` instead of the runner's target, since the job runs in that image. Actions pulls the image for the runner's CPU, so the same image on `ubuntu-24.04-arm` suggests `musl-aarch64`; an unresolved runner label (a matrix, an expression or an unknown label), a non-Linux runner, or a Windows container image is refused rather than guessed. A step that picks the job's Python (`setup-python`, or `setup-uv` with a `python-version`) installs it into the image, so that Python is suggested instead of the image's own and the image's libc still applies; `setup-python` has no musl builds, so it's refused in an Alpine image, and a container on `ubuntu-slim` is refused too. An expression, an `options:` that may change the platform, a job-level `services:`, a non-string or unsupported image, or any other container shape stays under "Couldn't read" rather than being guessed. ### Fixed

These came from independent second reviews of recent PRs, and a full audit of the codebase. (#55, #60)

- **Version ranges are respected.** `numpy>=1.26,<2` (or `~=`, `==1.26.*`) used to check the latest release (numpy 2.x). wheelgap now checks the newest release that matches the range (not yet narrowed by each release's `requires-python`).
- **uv.lock:** dependencies behind `[tool.uv] conflicts` (encoded as `extra == '...'` markers) were dropped as never installed, and path dependencies were treated as roots, so their dependencies counted everywhere. Markers with parts wheelgap can't know (extras, groups, `platform_release`, `platform_version`) now hold if they could hold for some value of those parts, while the platform and Python parts still apply. Poetry 1.x graphs also handle dependency cycles and version ranges on edges.
- **poetry.lock:** Poetry 1.x locks (lock-version < 2.1) keep markers only on dependency edges, so Windows-only packages such as pywin32 were reported missing on Linux. They're now walked like uv.lock. Dict markers that leave out an always-installed group, and packages with no files recorded, are handled too.
- **Free-threaded 3.15t `abi3t` wheels** (PEP 803) need `packaging` 26.3, which is now the minimum. `--explain` says when an `abi3t` wheel needs a newer CPython.
- **Python 3.7** targets use CPython's `cp37m` ABI, so their wheels are recognised.
- **PyPI lookups:** odd index responses give "unknown" instead of crashing; retries back off and honour `Retry-After`, retry dropped connections and skip permanent errors; an empty `WHEELGAP_INDEX_URL` means PyPI, and a `/simple` URL is a clear error; a missing pinned version says so ("version 1.0 not on index").
- **requirements.txt:** `-rfile` without a space, `--hash` with a space, comments after a tab, and `name@url` without spaces are all read correctly.
- **Output:** UTF-8 on Windows CI (no more "?" for ✓), `.python-version` files with a BOM, `--list-targets` uses the limits from `[tool.wheelgap]`, legacy `manylinux2014` wheels get the right `--explain` reason, more sdist formats are recognised, and `--macos 15` means 15.0.
- `--pyodide-lock`: a package whose lookup failed (e.g. a mistyped pin) was reported as bundled and could pass. It's now `unknown`, which fails.
- `pyodide-lock` in `[tool.wheelgap]` made every run without a matching Pyodide target exit 2. It's now quietly unused on those runs, and a relative path is read from the folder that holds `pyproject.toml`.
- **Yanked files:** a release pinned with `==` whose files have all been yanked was reported as having no files ("can't install"). pip still installs it (PEP 592), so its files now count, judged per target: they count only when every file that target could use is yanked.
- `pdm.lock`: packages with extras were listed twice (PDM writes one entry per extras variant). They now count once.
- The summary line could leave "unknown" packages out of its counts. Each gap package is now counted once, under its worst status.
- `quiet = true` in `[tool.wheelgap]` made `--json --explain` fail with a usage error. Quiet now only affects text output, `--no-quiet` turns it off for one run, and quiet runs still say why a package is unknown.
- `--explain`'s `via:` could credit a dependency group for a package that is also a runtime dependency. The project's own dependencies are now preferred.
- `--dockerfile` with an Alpine image plus `-t linux/arm64` checked glibc wheels. Docker platform names now keep the image's libc (musl).
- `--dockerfile`: Alpine 3.12 and earlier are checked against musl 1.1, not 1.2.
- `requirements.txt`: a bare VCS URL containing `@` (`git+ssh://git@github.com/...`) aborted the whole run. It's now skipped like other URLs.
- `python -m wheelgap.scan` now refuses to write results when more than 5% of lookups fail (`--max-error-rate`), records `lookup_errors` and each target's glibc/musl/macOS limits, and no longer counts Python 2-only wheels as "pure".

### Security

- Every GitHub Action used by wheelgap's own workflows is pinned to a full commit SHA, with Dependabot keeping the pins current, and PyPI releases now publish only from a `v*` tag through a protected environment. (#64)
