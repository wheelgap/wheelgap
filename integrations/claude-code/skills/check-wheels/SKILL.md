# Check wheels with wheelgap

wheelgap reads a lockfile and reports, per package and target platform, whether pip/uv would install a prebuilt **wheel**, build from **source** (slow, needs a compiler), or find nothing (**missing**). Lockfiles that record their files (`uv.lock`, `pylock.toml`, `poetry.lock`, `pdm.lock`) are checked offline in about a second; `requirements*.txt`, `Pipfile.lock`, `pixi.lock` and package names are looked up on PyPI.

## If the wheelgap MCP server is available

If the `wheelgap` MCP server is connected, prefer its tools to the command line: `check_lockfile`, `check_dockerfile`, `check_dist` (the `dist/` folder a release is about to upload), `diff_lockfiles`, `check_package` (one package, latest or a given version), `explain_install_failure` (the text of a failed install log), `suggest_targets` (the platforms and Pythons the project's CI files and Dockerfiles name) and `list_targets`. Their results are shaped differently from `--json`: `check_lockfile` and `check_dockerfile` return `ok` (true only when no package has a gap) and `gaps` (just the packages with one, each with its `results` and `error`); `diff_lockfiles` returns `worse`, `new` and `ok`. `check_lockfile`'s `passes` is the command line's verdict, which also accepts gaps on `advisory` targets and, with `fail-on = "missing"`, source builds. `check_package` takes `explain: true` to add `rejected`, and `dependencies: true` to also check everything the package installs, as `--deps` does: `dependency_gaps` lists each package in the tree with a gap, with its `results`, `gaps`, `via` path and its own `suggest`/`last_with_wheel`, and `ok` then covers the whole tree. For a pinned version with a gap, `check_package` also returns `suggest` (the newer release with the wheel) and `last_with_wheel`. `check_lockfile` takes `dependencies: true` too, for a requirements file, a conda `environment.yml`, `pyproject.toml` or a script's `# /// script` block (each gap gets `via` and `direct`). `check_dist` returns `dropped`, the targets the previous PyPI release had a wheel for that this one doesn't, and `ok` is false unless every target has a wheel and nothing was dropped (if the comparison with PyPI couldn't run, `dropped` is absent and `ok` is false; `passes` is the command line's verdict). Statuses, `unknown`, `skipped` and the advice below apply as for the command line. Pass paths as absolute paths or `file://` URIs, since the server's working directory may not be the project. To match a deployment, `check_lockfile` takes `extras`, `all_extras`, `groups`, `only_groups` and `no_dev`, as the command line's `--extra`, `--all-extras`, `--group`, `--only-group` and `--no-dev` do (without them it applies `groups` and `extras` from `[tool.wheelgap]`); the other tools take no selection. `check_lockfile` and `check_dockerfile` take `fix: true` to also return each gap's way out, as `--fix --json` does (see below): `fix` on each entry of `gaps`, `fix_summary`, and `gap_wheels` with `gap_wheel_index` and `gap_wheel_about`; it's refused with `offline`. `check_dockerfile` takes `inputs: true` to check the requirements files the final stage installs, as `--dockerfile-inputs` does, with `context` for the build context. `explain_install_failure` needs the `python` and `targets` of the machine the install ran on, since the log doesn't say. To set it up: `claude mcp add wheelgap -- uvx --from wheelgap wheelgap-mcp` (other clients: [MCP setup guide](https://github.com/wheelgap/wheelgap/blob/main/docs/mcp.md)); `uvx wheelgap@latest mcp` starts the same server. If uvx says "An executable named `wheelgap-mcp` is not provided", it's reusing a copy of wheelgap from before 0.9.0: run `uvx --refresh --from wheelgap wheelgap-mcp --version` once.

## Run it

```bash
uvx wheelgap@latest -p 3.13 -t linux-aarch64,musl-aarch64 --json
```

- **Input:** in the project directory, wheelgap finds `uv.lock`, `pylock.toml`, `poetry.lock`, `pdm.lock`, `Pipfile.lock`, `requirements.txt`, `requirements.lock` or `pixi.lock` (the first one present). With none of those at the root, it checks `pyproject.toml`'s direct dependencies, else the one requirements file under another name, else the one input up to 3 folders down, with a note saying which (`directory_inputs` in `--json`); when there are several to choose from it exits 2 and lists each as a command to run. Pass any other file by path, e.g. `uvx wheelgap@latest requirements-prod.txt …`. For `pixi.lock`, only the PyPI packages of one environment are checked (`--environment NAME`, default `default`); conda packages are `skipped`. A library with no lockfile: pass its `pyproject.toml` (direct dependencies only, unless you add `--deps`; add `--extra NAME` or `--all-extras`, and `--group NAME` or `--only-group NAME` for a `[dependency-groups]` group, since none is checked by default). A script with a `# /// script` block is read the same way (`uvx wheelgap@latest script.py …`, without running it), and its `uv lock --script` lock (`script.py.lock`) as a `uv.lock`. For a conda `environment.yml`, passed by path, the `pip:` list is checked as a requirements file and conda packages are `skipped`. To ask whether `pip install NAME` works on a platform, pass the name with `--deps`, which also checks everything it installs, resolved per target from PyPI's metadata, and `--explain` names the path to each gap (`uvx wheelgap@latest mcp==2.3.0 --deps -p 3.14 -t win-arm64 --explain` gives `via: mcp → PyJWT → cryptography`). Pin a version for a name that's also a subcommand (`mcp`, `diff`). `--deps` also resolves the whole tree a requirements file, `environment.yml`, `pyproject.toml` or script installs (a fully pinned `pip-compile` file is checked as written). It isn't pip's resolver: where pip would backtrack it stops with an error, so use a lockfile then. On the machine you care about, `python -m pip install --dry-run --ignore-installed --report report.json -r requirements.txt` then `uvx wheelgap@latest report.json -p <that Python> -t <that platform>` checks exactly what pip resolved there, without installing it.
- **Python (`-p`):** always pass the project's Python, from `.python-version`, `requires-python`, the CI matrix or the Dockerfile. Without `-p`, wheelgap uses `.python-version`, else the Python it runs on, which may be free-threaded (3.14t) and would report gaps an ordinary project doesn't have. Use `-p 3.14t` only to check free-threading readiness. To see what blocks a move to the newest CPython, check the project's Python next to it (`-p 3.13,next`; `next-t` for its free-threaded build): `blocking_newer_python` lists the packages with a gap only on the newer one.
- **Platforms (`-t`):** use what the project ships to.
  - A Dockerfile: `uvx wheelgap@latest --dockerfile Dockerfile --json` takes both Python and platform from the final stage (global `ARG` defaults included); if the build passes `--build-arg NAME=VALUE`, pass the same `--build-arg`. Add `--dockerfile-inputs` to check the requirements files the final stage installs with `RUN pip install -r FILE` instead of the project's lockfile (and `--dockerfile-context DIR` when the build context isn't the Dockerfile's folder, as in `docker build -f docker/Dockerfile .`); a Dockerfile it can't follow exactly is an error naming the line, never a guess. A `RUN` line it can't see into after the last install it reads (a script, `make`) gives a warning instead, in `dockerfile_warnings` with `summary.complete: false`: say the answer may miss what that line installs. For an image wheelgap can't read (`FROM ubuntu:24.04`, `nvidia/cuda`), pass both `-p` and `-t` with `--dockerfile`; `dockerfile_notes` says what that leaves unknown.
  - A `[tool.wheelgap]` table in `pyproject.toml`: its defaults apply with no `-p`/`-t`.
  - Otherwise run `uvx wheelgap@latest --suggest-targets --json` and confirm its suggestions with the user: it reads the targets and Pythons the project's GitHub Actions workflows, `.gitlab-ci.yml` and Dockerfiles name, each with its file and line, lists what it couldn't read, and checks nothing. Failing that, ask, or use `-t all` (the eight common platforms).
  - `uvx wheelgap@latest --list-targets` lists every target and alias.
- **Libc:** if the user names a deployment distro, pass `--distro NAME` (e.g. `ubuntu-22.04`, `debian-12`, `rhel-9`, `amazonlinux-2023`, `alpine`; `--list-targets` lists them). For a distro that isn't listed, verify its libc version and pass `--glibc X.Y` or `--musl X.Y`. None of these select platforms; Alpine still needs a `musl-*` target. With `--dockerfile`, leave `--distro` out: the image already sets the libc, and `--distro` would override it.
- **Private indexes:** packages a lockfile pins to another index are never looked up on PyPI: they keep their locked files, or are skipped as `private index` when the lock lists none, and `--index-url` doesn't change that. `--index-url URL` sends the lookups for requirements files, `pyproject.toml` and package names to that index (PEP 691 JSON), and `--offline` never contacts an index. wheelgap ignores the project's own index settings (an `--index-url` line in a requirements file, `[tool.uv]` indexes, `pip.conf`, `PIP_INDEX_URL`), so in a project that installs from a private index pass `--index-url` or check the lockfile, or those names go to pypi.org ([private indexes](https://github.com/wheelgap/wheelgap/blob/main/docs/how-it-works.md#private-indexes)).

## When an install already failed

If the user has the log of a failed pip, uv, Poetry or `pdm install -v` install, pass it to `uvx wheelgap@latest --from-log install.log -p <Python> -t <platform>` (or `-` for stdin): it finds the packages that failed to build and checks each as `--explain --suggest` does: why no wheel fits, and the release that has one.

## Read the result

- **Don't rely on the exit code alone:** `0` no failing gaps, `1` gaps, `2` bad input (with `--json`, stdout is then `{"error": {"message": ..., "type": ...}}`; the message is on stderr too). `--exit-zero` or `fail-on = "missing"` can make source builds exit 0, so read `summary.with_gaps` and each package's `results`.
- **`results`** maps a target label to `wheel`, `source`, `missing`, `unknown`, `n/a` (the package isn't installed on that target, per its markers) or `bundled` (shipped by Pyodide, with `--pyodide-lock`). Labels come from `targets[].label`: the platform alone with one Python, `"3.13 linux-x86_64"` with several.
- **`unknown`** means a lookup failed; the package's `error` field says why. Never report it as fine.
- **`skipped`** lists packages that weren't checked (editable, git, path, URL, private index), so don't claim every dependency was covered.
- **`pip_refuses`:** a `uv.lock` is answered the way `uv sync` installs it, and uv ignores `Requires-Python` upper bounds. With `--online`, a package's `pip_refuses` lists the files uv installs and pip would refuse, so mention them when the project installs these pins with pip.
- **`[tool.uv] environments`:** a `uv.lock` made with it covers only those environments, so a target outside them is an error (exit 2) naming the targets the lock covers, not a gap.
- **Installation scope:** with no selection, `uv.lock`, `poetry.lock` and `pdm.lock` checks conservatively include extras and development groups. To match a deployment, pass its selection: `--no-dev`, `--group NAME`, `--only-group NAME` (uv.lock, Poetry 2.x poetry.lock, pdm.lock) and `--extra NAME` (uv.lock, Poetry 2.x poetry.lock). Otherwise compare a reported gap with how the project is really installed before treating it as a deployment failure.
- **Why:** `--explain` adds each rejected wheel and the reason (`rejected`), and for `uv.lock` the dependency path that pulls the package in (`via`). For a package from PyPI that publishes an issue tracker, it also links it (`ask for a wheel: <url>`; `issues_url` in `--json`, `null` when there's none). The text and Markdown tables name the direct dependency behind a transitive gap, such as `cryptography (via mcp)` (with `+N` when more lead to it); `--json --explain` has the full path in `via` and the direct dependencies behind it in `direct`. `--explain --notes` adds the [coverage tracker](https://wheelgap.github.io/tracker/)'s known workarounds (`notes`), such as a binary package to use instead; it sends the names of packages with gaps to wheelgap.github.io. For a `linux-armv7l` gap (32-bit Raspberry Pi OS), `--explain --piwheels` says when [piwheels](https://www.piwheels.org/) has a wheel of that version, with the `--extra-index-url` line to install it (`piwheels` in `--json`).

## What to tell the user

1. Name the packages with gaps, per platform, with the reason from `--explain`, and which dependency pulls each in.
2. Offer concrete fixes. Start with `--fix` (`uvx wheelgap@latest … --fix --json`): for each gap it gives the way out, upgrade first. Each package's `fix` maps its gap targets to `kind` `upgrade` (`version`, the release to move to, and `how`, what to run for this input: `uv lock --upgrade-package NAME` for a uv.lock, the new pin for a requirements file, `poetry update NAME` (for a poetry.lock that records PyPI as its source); `constraint.allows: false` means the user's own requirement must be relaxed first), `gap_wheel` (no newer release has the wheel, but an unofficial one of the pinned version on wheelgap's [gap wheel index](https://wheelgap.github.io/wheels/) does: `wheel`, `url`, `sha256`), or `none` with a `reason`; an `upgrade` also names its fallback `gap_wheel`, or `null`. `fix_summary` counts them, and `gap_wheels` lists every cell a gap wheel fills. wheelgap doesn't resolve: after an upgrade, re-lock and run wheelgap again to check the release was picked and nothing else broke. The text output gives the commands. `--fix` sends gap package names to pypi.org (as `--suggest` does) and reads the gap wheel list from wheelgap.github.io; it's off with `--index-url` or a `WHEELGAP_INDEX_URL` mirror and refused with `--offline`, and it never changes statuses or the exit code. For the gap wheels:
   - The text output gives the lines to add for the input: `[[tool.uv.index]]`/`[tool.uv.sources]` for a uv.lock, `--extra-index-url` for a requirements file, the `# /// script` block for a script. `--fix --print-gap-wheel-snippet` prints only those, for one `uv.lock` (not a script's), one requirements file or package names.
   - For a uv.lock, follow the output's note on a package that isn't a direct dependency: uv applies `[tool.uv.sources]` to direct dependencies only, so it must also be listed where the dependency that brings it in is.
   - For other lockfiles, the output only says to add the index where that lockfile is made and lock again: never invent `[tool.uv]` or `--extra-index-url` lines for them. A pdm.lock, and a poetry.lock package that records no index (the usual case for PyPI packages), get no gap wheel or upgrade from `--fix`: wheelgap can't tell they come from PyPI, and a `wheelgap: note:` says so.
   - Gap wheels are built by wheelgap from the PyPI sdist, not by the package's maintainers: tell the user so, and ask before adding the index to a project file.
   - Never suggest the index in a project that installs from a private index: pip treats every index alike (the output's caveat says why that matters), and wheelgap can't see an index set in `pip.conf`.
   - wheelgap doesn't read the project's index settings, so for a requirements file, `pyproject.toml`, an `environment.yml`'s `pip:` list, package names or a script, a re-run after adding the index still reports the gap: don't loop on it. (A `uv.lock` or `poetry.lock` locked again with the index records the gap wheel's file, so its re-run counts it as `wheel`; a `Pipfile.lock` records no file names, so its re-run skips the package as `private index`; a new pip report in which pip took the gap wheel skips it as `url`, since the file didn't come from PyPI, or refuses the report (exit 2) when nothing in it came from PyPI.)
   - An empty `gap_wheels` doesn't prove there is none: it's also `[]` when the run uses another index or the list couldn't be read, and a `wheelgap: note:` on stderr says when it couldn't.

   Other fixes:

   - pin a version that ships the wheel (`--explain --suggest` names the nearest newer release with one, `suggest` in `--json`; when no newer release has one, it names the last older one that did, `last_with_wheel`; `--deps --explain` turns it on by default, `--no-suggest` turns it off). `--write-constraints FILE` also writes those pins as a pip/uv constraints file; it isn't checked against the rest of the tree, so check it with `pip install -c FILE …` or `uv pip compile -c FILE …`;
   - use a `-slim` Debian base instead of Alpine;
   - add build dependencies to the Dockerfile on purpose (`--explain --build-info` says what each source build needs, such as a Rust toolchain or CMake; it downloads sdists);
   - `--fail-on missing` to accept source builds in CI.
3. To accept a known gap without hiding it, use `--ignore NAME` or `ignore = ["NAME"]` in `[tool.wheelgap]`, or `--ignore NAME:TARGET` to accept it on one platform only. To watch a platform the project doesn't support yet without failing on it, add it to `-t` and pass `--advisory TARGET` too (or `advisory = [...]`): its gaps are reported but don't fail the run.

## After a dependency upgrade

`uvx wheelgap@latest diff OLD NEW -p 3.13 -t linux-aarch64 --json` lists the packages that got worse on a target and the new packages with gaps (exit 1 if any). `OLD` can be a git ref such as `origin/main:uv.lock` or `HEAD:uv.lock` (the path is relative to the repository root; fetch the base ref first in a shallow CI checkout); a package that can no longer be checked counts as worse. For a `-p`, `-t` or libc floor you don't pass, `diff` reads `[tool.wheelgap]` and `.python-version` from the `NEW` lockfile's project (the MCP `diff_lockfiles` tool doesn't, so pass them there). With a dependency graph, `direct` on a `worse` or `new` entry names the direct dependencies that bring the package in. `diff NAME==OLD NAME==NEW --deps` compares everything two releases of a package install, without a lockfile. In GitHub Actions, the wheelgap Action's `compare-to: base` runs this on each pull request.

## Before a release

For a package the project publishes, `uvx wheelgap@latest --dist dist -p 3.13 -t win-arm64,linux-aarch64 --json` checks the wheels and sdist about to be uploaded and fails when a target the previous release on PyPI had a wheel for has none in these files (`dropped` in `--json`). The GitHub Action's `dist: dist` input runs the same check before the upload step. `--badge PATH` also writes a shields.io endpoint file with how many targets have wheels for everything (`7/8 targets`), even when the check fails, for a README badge.

wheelgap checks wheel availability only, not whether a package works without the GIL.

For a quick look at one popular package without running anything, fetch `https://wheelgap.github.io/tracker/data/packages/<normalized-name>.json`. That's a nightly scan of the **latest release** of the top 5,000 PyPI packages, not the version a project pins.
